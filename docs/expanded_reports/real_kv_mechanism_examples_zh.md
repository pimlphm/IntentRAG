# 真实 KV 复用的三个事后机理个例

这些个例来自已经完成的 594 个运行配置，按“高共同前缀但索引打断”“稳定祖先索引”“没有共同源证据”三种现象事后选取，目的仅是解释机理，不是新增验证集。每个个例都在同一方法、同一问题对上对照三个布局。完整源证据编号、实际发出的证据、祖先元组、字符串首处分歧和原生引擎计数保存在同名 JSON/CSV 中。

## 个例一：高复用也可能来自粗粒度证据占满预算

Boeing 737 的同一组襟翼超速相关问题，在 IntentRAG balanced 设置下，问题前置布局仅复用 66 个输入 token；规范证据前置布局复用 1,670/1,709 个输入 token（97.72%），仅需新计算 39 个；祖先索引前置后，复用量却下降至 90/1,841（4.89%），新计算量为 1,751 个。

这并不是完整 Top-10 证据都获得有效复用。规范布局排序后的首条共同证据是发动机／滑油类 component profile，其截断片段单独占满 1,600 个源上下文 token 的预算，种子与目标实际发出的源正文完全相同。原始 Top-10 仅有 4 个共同编号，实际输入却只保留了这个共同的粗粒度单元。高复用因此可能反映“共同粗层级占据预算”，而不反映对襟翼问题局部支持的完整覆盖。

祖先索引由完整检索集合生成，种子第一条元组为 `SEC_0026 / no_component`，目标第一条为 `SEC_0001 / engine_oil_powerplant`。虽然后面的证据正文相同，插在正文之前的这处分歧会中断顺序前缀命中。这证明本次实现中的位置机制，不证明所有层级记忆方法都会降低复用，也不证明该共同发动机 profile 可以支持襟翼处置。

可放入正文的短说明：**复用率受到证据排列和预算截断共同影响。共同的粗粒度状态可以形成近乎完整的缓存前缀，同时排挤查询局部证据；而位于前缀上游的可变路由元数据，即使不改变后续正文，也可能切断实际 KV 复用。**

## 个例二：稳定长期索引增加缓存计数，但未增加证据支持

仍是上述同一问题对，Profile-resolved 方法中，规范布局复用 859/1,709 个输入 token；祖先索引前置布局复用 985/1,835 个。两者都需新计算 850 个 token。此时种子和目标的祖先索引元组完全一致，包含同一文档、章节和 flight_control 类别，两个规范源正文也以相同的前两条证据开始，因此插入的 126 个共同索引 token 可以一并复用。

这里多出来的 126 个 cached token 恰好等于新增的前置元数据量，并非增加了 126 个可支持答案的源证据 token。因此应区分稳定索引带来的计算复用与叶级源证据带来的支持。长期索引的作用是稳定路由和定位；其本身不替代当前问题需要的具体条件、步骤及出处。

可放入正文的短说明：**层级元数据是否有利于前缀缓存，取决于它能否跨查询保持字节级稳定。共同索引可以增加实际命中计数，但这部分增量不应被计入答案证据的保留量。**

## 个例三：没有共同叶证据时，前置也不能制造复用

Cessna 172 的方向舵／升降舵平衡问题与副翼警告问题，在 Long-term fixed 设置下，Top-10 证据集合无共同编号。规范布局分别以不同文档中的不同源单元开始。问题前置、规范证据前置、祖先索引前置的实际复用量分别为 59、66、69 个输入 token；规范布局仍需新计算 1,643 个 token。

这些少量命中主要发生在共同系统提示、飞机范围和源头部的固定文本中，不能写成“零 KV 命中”，也不能解释成有效叶证据复用。同属一架飞机、同属飞控主题，没有使两个问题的局部证据正文成为共同前缀。原文来源中的组件标签和宽主题代理也不等于专家认证的适用范围。

可放入正文的短说明：**长期主题相近并不足以产生局部证据复用。规范化可以稳定已经存在的共同前缀，却不能把不同叶证据转化成同一支持状态。**

## 对方法论的启示与边界

这三个个例解释的是顺序前缀缓存的首处分歧机制，不是互信息估计。高缓存比例既可能来自共同的有用状态，也可能来自粗粒度背景占据预算；缓存 token 总数还混合了系统头、路由索引和源证据。信息组织的科学问题因此是：稳定了哪些信息，挤掉了哪些查询局部信息，以及稳定部分是否仍有可追溯、适用的支持，而非仅判断前缀更长。

相应的组织原则是将真正稳定、且具有兼容范围的长期状态放在可复用区，把查询相关的动态路由、叶级证据和条件检查放在后续区，并单独核算元数据复用与证据支持。若签名要求飞机、部件、条件、来源版本或权限发生变化时失效，失效逻辑还需要独立元数据或专家标签来验证。本次三个布局均将 revision、authority 标记为 unverified，不能把它们当成 signed-admissibility purity 已经得到真实验证。

32-token 生成探针只检验实际引擎计数和短输出的一致性；所有 timing 均存在同 GPU 的其他任务负荷，不能把这些个例用于孤立吞吐加速或完整问答正确率结论。
